# PartCore review — 2026-11-12

> **v1.2 note (2026-11-12):** the kernel was since renamed **engine.solid** and moved to the library repo (`withshalom/getlibrarycraft`, branch `engine/solid`, code in `lib/solid/`). This review is kept as written, with its PartCore-era names and paths.

> Written when the kernel was still called KNOT. Names and paths below were updated to PartCore (`app/partcore/`, branch
> `partcore`) after the owner named it the same day. The findings are unchanged.

This review covers four things:
- the PartCore handoff plan (v1.0)
- what PartCraft already contains (the S0 audit)
- KUBIC.html and KARVE.html, as supplied by the owner
- what changes in the plan because of them (now v1.1, `HANDOFF.md`)

Every claim below was read in the code. Anything inferred says so.

---

## 1. Headline

**PartCraft already has most of the NURBS geometry the plan was going to write.** It also has a STEP B-rep evaluator and
an ACIS reader. The plan assumed a blank slate (S4–S10 from scratch, a separate repository), and that is wrong.

PartCore's real job is the layer PartCraft does not have: **exact B-rep topology.** That means:
- edges that are shared, exact curves with pcurves on both faces
- trims that are exact curves rather than polygons
- solids that are valid by construction and checked by an independent auditor
- STEP written with exact edge curves
- no mesh booleans

So the plan keeps its architecture, numerics, topology, audit and roadmap shape, but it is rebased onto cc-nurbs,
cc-step and cc-acis, and it lives in this repository under `app/partcore/`. The details are in §5.

## 2. What PartCraft already has (S0 audit)

All of it is DOM-free and Apache-2.0, written from published sources (each file cites them), and in the same style as
the plan: untrusted input checked, errors as codes, reports that state measured deviations.

### 2.1 cc-nurbs — `app/nurbs/` (20 files, 6,816 lines; byte-identical copy in `tests/lib/nurbs/`)

**Health:**
- **`tests/tools/nurbs/test.mjs`: 173 passed, 1 failed.** The one failure is "ModelCraft and PartCraft copies
  byte-identical (sync --check)", which needs the CadCraft monorepo layout, not this fork.
- `test-trim.mjs`: 25 of 25 passed.
- `test-solid.mjs` needs the vendored manifold-3d, so it was not run here.

**Constraint:** cc-nurbs is canonical in the monorepo's `lib/nurbs`, and ModelCraft and PartCraft carry byte-identical
copies (`tools/nurbs/sync.mjs`). So **PartCore must not edit `app/nurbs/` in place.** It imports it, and any fix it needs
goes to the canonical copy upstream (decision D-ccn).

### 2.2 cc-step — `app/step/`

- **`read.js`** reads AP203 / AP214 / AP242 B-reps, faceted B-reps and AP242 tessellated faces, with assembly placement.
  The output is **triangles**: `positions`, `indices` and `triFace` per solid, plus notes and counts.
- **`geom.js`** evaluates *and inverts* the STEP geometry entities: line, circle, ellipse, polyline, B-spline, plane,
  cylinder, cone, sphere, torus, revolution, extrusion and offset surfaces. It handles periods, poles and per-direction
  scale.
- **`tess.js`** discretises each edge once, shared by its two faces, so shells stay closed. Faces are triangulated in
  (u, v), with periodic directions unwrapped and poles split, by ear clipping plus Delaunay flips.
- **`part21.js`** is a one-pass ISO 10303-21 index plus a lazy parameter parser (complex instances included).
- **Covers:** S28 (parser: done), most of S30's geometry (evaluators: done), and S15–S16's ideas (shared edges, seams and
  poles). What PartCore adds is building B-rep *topology* instead of triangles.

### 2.3 cc-acis — `tests/lib/acis/` (test copy of the monorepo's `lib/acis`; not in `app/`)

- SAT / SAB → topology and geometry, by ACIS version.
- Planes, cones, cylinders, spheres, tori and B-spline `exactsur` surfaces.
- Edges: lines, ellipses and B-spline `intcurve`s.
- Its own **constrained Delaunay triangulation (`cdt.js`)** and a tessellator that handles seams and poles.
- **S33 shrinks** from "write a SAT reader" to "lift cc-acis' model into PartCore topology". `cdt.js` is the first candidate
  for S16.

### 2.4 The rest of PartCraft that matters here

- `kernel.js`: the manifold mesh kernel that builds every part today.
- `brep*.js` and `exact-client.js`: the OpenCascade route, opt-in and absent from builds since 0.4 for licensing.
  `ExactKernel` starts `brep-worker.js` and is called as `k.call('regen', { part })`. That message protocol is the seam
  PartCore plugs into (S36).
- `sketch*.js`: PartCraft's sketcher (arcs, intersections, splines). Not read in this review.
- `cam-*.js`: PartCraft already has a CAM stack. From the file names it covers adaptive clearing, offsets, finishing,
  cycles, posts and a post editor, simulation and tool tables. Not read in this review.
- `PROVENANCE.md`: "Features that need an exact B-rep kernel say 'Not built yet'". PartCore is what turns those on.

## 3. KUBIC (`reference/kad/kubic/KUBIC.html`, 1,476 lines)

**What it is:** a single-file, Canvas2D 3D sketcher.
- **Frame:** Z-up camera; sketch on XY at Z = 0, the same frame as KAD and the plan.
- **Tools:** line, 3-point arc, rectangle, circle, polygon, line-line fillet, offset, extrude.
- **Files:** `.kbc` save/open (v2.0), binary STL export and STL import.
- **History:** `KUBIC.html` is the current name. Its code is identical to the older `KUBE.html` apart from KUBE → KUBIC
  and `.kbe` → `.kbc`.

**What it is not:** a solid modeller. A "solid" is `{ base: [polygon points], height }`, a prism with faceted sides.
There is no B-rep, no NURBS, no topology and no booleans. The KADsuite card says "push/pull and booleans"; neither
exists in the code.

### 3.1 Problems the kernel fixes (by design)

| # | Where | What happens | PartCore fix |
|---|---|---|---|
| K1 | `findLoops` (859) | Circles become 48-gons before extruding | S7 / S19: exact circles, cylindrical sides |
| K2 | `findLoops` | `ARC` objects are never used. A sketch that KUBIC's own Fillet tool has touched has lines with dangling ends, so the line-loop test (*every* vertex of degree 2) fails and **a filleted outline cannot be extruded** | S19: chain lines, arcs, circles, polylines and splines |
| K3 | `findLoops` | Only one line loop is found, starting from the first vertex. Other loops are dropped silently; one stray line disables all line loops | S19: find every loop, report what is left over |
| K4 | `doExtrude` | Each loop becomes its own prism, so a circle inside a rectangle gives two overlapping solids, not a plate with a hole | S19: loop nesting (outer / holes) |
| K5 | `solidFaces` | Assumes the outline is counter-clockwise. A rectangle dragged right-to-left or top-to-bottom, or a line loop walked the other way, gives an **inside-out solid** (and STL) | S12 / S19: orientation from signed area; audit |
| K6 | `doExtrude` | Negative heights are accepted, which also turns the solid inside out | S20: two-sided / reversed extrude, audited |
| K7 | `exportSTL` | Caps are fan-triangulated ("all prism faces are convex"). Any concave outline (an L, a U) writes **wrong, overlapping triangles** | S16 / S17: constrained triangulation |
| K8 | `exportSTL` / `stlToSolid` | Export writes model units as they are (inches in inch mode). Import divides by 25.4 in inch mode. The two do not round-trip | S17: exporters in mm, unit at the boundary |

### 3.2 Bugs to fix in KUBIC itself (not the kernel's job)

| # | Where | What |
|---|---|---|
| K9 | `stlToSolid` (1358, 1368) | `nextSolidId` is never declared. In strict mode **every STL import throws** ("STL error: nextSolidId is not defined") |
| K10 | `drawRawMesh` (595) | Uses an undefined `ctx` and calls `project([x,y,z])` with an array, then reads `.x / .y` from an array result. Never reached because of K9, broken once K9 is fixed |
| K11 | `stlToSolid` | The prism reconstruction feeds *every* triangle edge of the bottom face, internal diagonals included, to `reconstructPolygon`. Only edges used once are the outline |
| K12 | `commitOffset` | A polyline offset moves each vertex along its neighbours' normal (no miter), so corners come out at the wrong distance. Lines always offset to the same side |
| K13 | `setTool` (852) | The fillet row is shown for every tool (`'flex' : 'flex'`) |
| K14 | `drawSolids` | Faces are depth-sorted within one solid only, so overlapping solids draw in the wrong order |
| K15 | head (41–42) | Loads Google Fonts from the network. Breaks the offline rule (D2): bundle the two fonts or use system fonts |

### 3.3 What KUBIC gives PartCore

- The **profile input format** (`Sketch`: `LINE`, `ARC {startA, endA, ccw}`, `CIRCLE`, `POLYLINE {pts, closed}`). The
  S19 adapter reads it unchanged.
- The **first acceptance target for S20**: draw a KUBIC sketch, extrude it, and get an audited body plus a correct STL.
- The **`.kbc` file** that needs a `bodies` section, the same question as D-kad for `.kad`.

## 4. KARVE (`reference/kad/karve/KARVE.html`, 969 lines)

**What it is:** a single-file lathe/mill front end.
- **Flow:** units → mode → material (21 lathe and 23 mill grades with speed factors and notes) → stock dimensions →
  operations → G-code preview → `.nc` export.
- **Version:** the owner's file differs from `withshalom/KARVE` `main` only in header lines (year and trademark list).

### 4.1 Safety: do not run its G-code on a machine

`generateGCode` emits fixed moves that are not computed from any geometry. I read each one:
- **Feeds per revolution are written as feeds per minute.** Lathe feeds `0.15 / 0.20 / 0.12` are mm per revolution
  values, but the program header is `G94` (per minute) for both modes. Inch mode converts nothing, so a mill feed of
  `600` becomes **F600 in/min under G20**.
- **Radius or diameter mode is not set.** X is written as a radius (`od/2 + 2`), but neither `G7` nor `G8` is emitted.
  On a lathe in diameter mode the "turn" pass would cut from Ø50 to about Ø26 in a single pass.
- **Most moves cut air or slot through.** Face runs at `Z2.0`, 2 mm in front of the face. Turn runs outside the stock
  radius. Mill face runs at `X-10`, off the stock. Profile, drill, thread and contour all fall through to "plunge at the
  centre, feed to `X = w`", which cuts a slot to the edge. The pocket is one rectangle with no tool diameter and no
  stepover.
- **Fixed depths.** Drill is always `Z-25` and thread is always `Z-18` with pitch 1.5, whatever the stock.
- **Dialect.** The program claims LinuxCNC, but `G76 X… Z… P8 Q0.1 F1.5` does not match LinuxCNC's G76 words (pitch as
  `P`, plus `I`, `J`, `K`). `G83` is emitted without an `R` plane. I expect a LinuxCNC interpreter to reject both lines;
  this is from the dialect's documentation as I know it and was not tested on a controller.
- **Missing.** No tool change (`T… M6`) and no coolant.

### 4.2 Other findings

| # | What |
|---|---|
| V1 | **Import is broken.** `importKBE` reads `.kbe` with lower-case `line` / `rect`, but KUBIC writes `.kbc` with upper-case `LINE / ARC / CIRCLE / POLYLINE`. Nothing from KUBIC imports |
| V2 | `drawLathe` draws the bore at x = 0 and x = −R, not at the bore radius |
| V3 | `updateStockInfo` writes `&middot;` through `textContent`, so the entity shows literally |
| V4 | Google Fonts from the network (offline rule) |
| V5 | "Open in KODE" only shows a toast |

### 4.3 What KARVE gives PartCore

- The **material table** and the **operation vocabulary**.
- Not its toolpaths. PartCraft's CAM stack is the place toolpaths come from.

What PartCore gives KARVE:
- **Lathe:** an exact turned profile, as a revolve half-section (S21, S26).
- **Mill:** exact planar sections and outlines of planar faces (S26).

Recommendation: KARVE consumes PartCraft's CAM through PartCore geometry rather than growing its own generator.
